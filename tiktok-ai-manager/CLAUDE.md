# Протокол работы — TikTok AI Manager (@gulyashik52)

Этот файл — рабочие правила ассистента по проекту. Он важнее любых общих
соображений о том, «как обычно работает TikTok».

## Главный принцип

Решения принимаются на основании данных этого аккаунта. Не на основании
общих представлений об алгоритмах, не на основании чужих кейсов.
Если данных нет — это говорится прямо, а не заменяется правдоподобной
формулировкой.

## Обязательная маркировка

Каждое содержательное утверждение помечается:

- **FACT** — подтверждается данными в `data/`. Обязана сопровождаться
  числом и указанием N, на котором посчитано. Без числа это не FACT.
- **HYPOTHESIS** — правдоподобно, но не проверено. Обязана сопровождаться
  указанием, какой эксперимент или какие данные её проверят.
- **RECOMMENDATION** — предлагаемое действие. Обязана ссылаться на
  конкретный FACT или на HYPOTHESIS, которую проверяет.

Утверждение без маркировки считается ошибкой.

## Пороги доказательности

- Закономерность не может быть переведена в **FACT** при `N < 25` роликов.
  Текущий порог задан в `analysis/describe.py` (`MIN_N_FOR_PATTERN`).
- Закономерность, наблюдаемая только на выбросах, не является
  закономерностью. Два ролика этого аккаунта дают 97,8% всех просмотров —
  любая статистика считается и с ними, и без них, и обе цифры показываются.
- Корреляция не выдаётся за причинность. Для каждой корреляции явно
  называется конкурирующее объяснение (в первую очередь — обратная
  причинность).

## Запреты

- Не придумывать метрики, которых нет в `data/`.
- Не заполнять пропуски «типичными» значениями.
- Не сравнивать свежий ролик со зрелым по абсолютным числам: сравнение
  корректно только при сопоставимом возрасте публикации (см. снимки).
- Не публиковать и не ставить в очередь ничего без явного подтверждения
  владельца аккаунта.

## Источники данных и их роли

| Что | Откуда | Примечание |
|---|---|---|
| reach, completion rate, avg view time, favorites, точная длительность | **Supermetrics** (`TIKBA`, report_type `videos`) | аналитическое ядро |
| comments | оба | подтверждено EXP-004: совпало 16/16 |
| views, likes, shares | оба | используются для сверки |
| планирование и публикация | **Metricool** (`createScheduledPostForReview`) | только через ревью |
| источники трафика (For You / Hashtag / Sound / Search) | **недоступны** | поля есть в каталоге Metricool, но возвращают null |

### Статусы сверки

| Статус | Смысл | FACT |
|---|---|---|
| `both_matched` | оба источника дали одно значение | разрешён |
| `both_expected_transform` | различие по известному правилу (`metricool = floor(supermetrics)`) | разрешён |
| `both_lagged` | **доказанное** отставание: значение отстающего в точности равно более раннему значению канонического | разрешён |
| `single_source` | метрику отдаёт только один источник | разрешён |
| `untested_overlap` | метрика есть в обоих, запрошен один | **запрещён** |
| `both_discrepancy` | расхождение неизвестной природы | **запрещён** |
| `unavailable` | не отдаёт ни один источник | **запрещён** |

FACT опирается на статус **именно той метрики**, для которой выводится:
доказанное отставание по `views` не разрешает FACT по `reach`.

### Правило both_lagged

Статус присваивается только при одновременном выполнении всех условий:

1. метрика входит в белый список монотонных счётчиков
   (`views`, `likes`, `shares`, `comments`; расширяется явно);
2. у канонического источника не менее двух наблюдений и существует более
   раннее A(t1) < A(t2);
3. значение отстающего источника B(t2) в точности равно A(t1);
4. не выполняется B(t2) > A(t2);
5. различие не объясняется известным преобразованием — такие случаи остаются
   `both_expected_transform` и никогда не переклассифицируются;
6. наблюдений достаточно; иначе `both_discrepancy` или `untested_overlap`.

Канонический источник **определяется наблюдениями для конкретной пары
(ролик, метрика)**, а не назначается источнику навсегда. Обязательно
сохраняются `canonical_source`, `lagging_source`, `lag_basis` и ссылки на
наблюдения-доказательства.

Формулировка нейтральна: «источник отстал от канонического наблюдения».
Запрещено писать, что источник ошибся или что его данные неверны.
Конкурирующее объяснение — независимое чтение и случайное совпадение —
сохраняется вместе со статусом и не считается исключённым.

При расхождении неизвестной природы вывод не делается: расхождение
фиксируется и разбирается. Сверка выполняется на каждом запуске.

## Формат данных

- `data/raw/` — сырые выгрузки как есть, с датой и параметрами запроса.
  Не редактируются никогда.
- `data/videos.jsonl` — неизменяемые свойства ролика (id, дата, описание,
  длительность, хештеги). Append-only.
- `data/snapshots.jsonl` — метрики на момент замера. Один ролик даёт много
  строк: по одной на источник и на дату снимка. Метрики растут во времени,
  поэтому хранится история, а не последнее значение.
- `db/` — SQLite, собирается из JSONL, в git не попадает.

JSONL, а не SQLite, — потому что бинарный файл не даёт читаемых диффов и
не переживает эфемерное окружение осмысленно.

## Рабочий цикл

1. Выгрузка → `data/raw/` с датой.
2. `python3 analysis/normalize.py` — сверка источников и обновление JSONL.
3. `python3 analysis/describe.py` — пересчёт статистики.
4. Интерпретация → `content/dna.md`, с маркировкой и ссылкой на цифры.
5. Гипотезы → `experiments/register.jsonl` до публикации, а не после.
6. Коммит. Данные существуют, только если закоммичены.
