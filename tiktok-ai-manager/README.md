# TikTok AI Manager — @gulyashik52

Помощник для TikTok-аккаунта. Разбирает, что залетело и чем это отличается
от остального; предлагает, что снимать дальше; раскладывает идеи по дням так,
чтобы каждая публикация проверяла одну гипотезу; через 30 дней подводит
итог по правилу, записанному заранее. Решения — по данным этого аккаунта,
а не по общим представлениям об алгоритмах. Сам ничего не публикует.

## Быстрый старт (Windows)

Нужны Git for Windows и Python 3.11+ (проверить: `git --version`,
`python --version`).

Первый раз:

```cmd
cd %USERPROFILE%\Desktop
git clone -b claude/tiktok-manager-env-audit-8mh3mg https://github.com/cerfus/--- tiktok-ai-manager
cd tiktok-ai-manager\tiktok-ai-manager
python -m pip install -r requirements.txt
```

Папка уже есть, но версия старая — в ней `git pull`. Если он пишет
*Your local changes … would be overwritten*: это производные файлы из
`data/`, их пересобрала программа. `git stash`, затем снова `git pull` —
ничего не теряется (`git stash` откладывает изменения, а не удаляет).

Запуск — **двойной щелчок по `AI-Manager.bat`** (ярлык на рабочий стол:
правая кнопка → «Отправить» → «Рабочий стол»). Меню само проверит
готовность и скажет, чего не хватает. База PostgreSQL нужна только для
пунктов «Статус» и «Отчёт» — разбор, идеи, план и дашборд работают без неё.

## Как пользоваться

При запуске меню сверху написано, **что делать сейчас**: ближайшая
публикация по плану и следующий шаг.

1. **Пункт 6 — план** на 3 недели и календарь `.ics` (напоминание за час,
   день итога через 30 дней).
2. **Перед съёмкой — 5 → 2** «взять идею в работу»: база сравнения
   фиксируется ДО публикации.
3. **Выложили — 5 → 3**, ссылка на ролик. Сразу, выгрузку ждать не нужно.
4. **Через 30 дней — 5 → 4** «подвести итог»: его выносит правило,
   записанное при регистрации, а не впечатление.
5. **Раз в неделю — пункт 10** «Обновить программу из GitHub»: новые данные
   (по понедельникам их забирает облачная Routine), новые идеи, исправления.

Ещё: пункт 3 — что залетело и почему, пункт 4 — новые идеи, пункт 7 —
дашборд в браузере, пункт 9 — как алгоритм раздаёт ролики и план улучшения,
пункт 13 — готовность программы.

### Обновление

Обновляться — **пункт 10 «Обновить программу из GitHub»**.
Он сам сохраняет свои эксперименты и идеи коммитом, откладывает в
`git stash` пересчитанные на ПК данные (эталон — в GitHub), делает
`git pull` и дозагружает базу. Не слилось — слияние отменяется, всё как
было. Пункт 11 отправляет свой журнал экспериментов и идеи в GitHub —
их увидят сессии Claude. Если `git pull` делали руками — пункт 12
«Обновить базу после ручного git pull».

Если после обновления обновились сами `.bat`, программа попросит
закрыть окно и запустить `AI-Manager.bat` заново.

**Данные из Metricool обновляются сами раз в неделю** (понедельник, 08:47
по Москве): облачная сессия Claude забирает выгрузку, прогоняет все
проверки и кладёт данные в GitHub. На ПК после этого — пункт 10.
Если проверки не прошли, данные не кладутся, а причина приходит в
уведомлении. **Один раз нужно подключить Metricool к этой Routine:**
claude.ai → Routines → «TikTok: еженедельное обновление данных» →
коннекторы → Metricool (сессия, создавшая Routine, передать коннектор не
может). Без него Routine ничего не делает и пишет, что подключить.

## Устройство: база и пересборка

Требуется PostgreSQL 16 (SQLite не поддерживается).

```bash
bash scripts/bootstrap_db.sh        # БД, три роли, .env с правами 600
python3 db/migrate.py               # миграции от имени владельца схемы
python3 normalize/normalize.py      # raw -> JSONL (источник истины)
python3 db/load.py                  # JSONL -> PostgreSQL
bash scripts/verify_all.sh          # пересборка с нуля + все тесты
```

### Windows, без WSL

```cmd
scripts\menu.bat                    REM меню: статус, отчёт, разбор, идеи, ингест
scripts\migrate.bat --adopt         REM миграции (idempotent)
scripts\verify_all.bat              REM все проверки, БД не пересоздаётся
```

Логика живёт в `scripts\verify_all.py` и одинакова на обеих системах;
`.bat` только находит Python и включает UTF-8. Шаг пересборки БД требует
`DROP DATABASE`, на который роли проекта не имеют права (в 0001 они
созданы с `NOCREATEDB`), поэтому он запрашивается явно —
`scripts\verify_all.bat --rebuild` при заданном `TIKTOK_DSN_SUPER`. Без
запроса шаг помечается **ПРОПУЩЕН** и за пройденный не выдаётся.

**PostgreSQL источником истины не является.** База пересобирается из
`data/*.jsonl` командой `scripts/rebuild_from_jsonl.sh`, и слепок состояния
после пересборки обязан совпасть побайтово.

Роли: `tiktok_owner` владеет схемой, `tiktok_rw` работает в рантайме без
UPDATE и DELETE на append-only таблицах, `tiktok_ro` только читает.
Пароли генерируются при бутстрапе и живут в `.env`, который в git не попадает.

## Советник: что снимать дальше

Пункты 3 и 4 меню (или `python -m advisor.run analyze` / `ideas`):

* **Что залетело и почему** — разбор только по данным аккаунта. Молодые
  ролики (< 30 дней) со зрелыми не сравниваются; признак становится
  гипотезой, только если отделяет хиты от остальных.
* **Идеи** — с ключом `ANTHROPIC_API_KEY` в `.env` и пакетом
  `python -m pip install -r requirements-advisor.txt` их придумывает модель Claude
  (`claude-opus-5-5`); без ключа — шаблоны экспериментов, бесплатно.
  Ответ модели проходит проверку: идея без проверяемой гипотезы, с числом,
  которого нет в данных, или с обещанием результата отбрасывается, и
  причина показывается. Сохраняется в `data/ideas/`.

Ключ берётся на console.anthropic.com и оплачивается отдельно от подписки
claude.ai.

Идеи можно получить и без ключа — в рабочей сессии с Claude: ответ в схеме
`advisor/ideas.py` (SCHEMA) сохраняется командой
`python -m advisor.run ideas --payload ответ.json` и проходит **те же**
проверки, что ответ API; источник в файле назван честно — «рабочая сессия».

Время публикации проверяется в двух поясах — UTC и поясе бренда из
настроек Metricool (Europe/Moscow): гипотеза, которая держится только в
одном, помечается «зависит от часового пояса». На Windows для этого нужен
пакет `tzdata` (он в `requirements.txt`); без него разбор работает,
но местное время не считает и говорит об этом.

**Эксперименты** (пункт 5 меню): взять идею в работу — до публикации,
база сравнения фиксируется сразу; после выхода ролика — привязать его
ссылкой сразу после публикации, выгрузку ждать не нужно (дату бот берёт
из номера ролика и перепроверит, когда ролик придёт в данных); через
30 дней бот сравнит просмотры с базой и с роликами того же периода вне
гипотезы (контроль). Ролик, вышедший раньше регистрации, не привязывается.
Идеи под одну гипотезу собираются в один эксперимент: для итога нужно
5 зрелых роликов. Итог выносит правило, записанное при регистрации, а не
впечатление: пункт 5 → 4 покажет его и закроет эксперимент с вашего
согласия.

**План публикаций** (пункт 6 меню, `python -m advisor.plan`): раскладывает
сохранённые идеи по дням на 3 недели, начиная с сегодня (если до слота
не меньше 2 часов) — один ролик в день, каждый в
час, который проверяет его гипотезу и не попадает в окна остальных
гипотез о времени (если развести нельзя, план так и пишет). Рядом
кладётся календарь `data\runtime\plan.ics`: двойной щелчок добавляет
события в Outlook / Google / iPhone — публикация с напоминанием за час и
день подведения итога через 30 дней. Выкладывает ролик человек: программа
ничего не публикует.

**Как алгоритм раздаёт ролики** (пункт 9 меню, `python -m advisor.algorithm`,
в Telegram — `/algo`): разбор поведения раздачи по данным этого аккаунта —
устройство TikTok в данных не видно, поэтому о нём ничего не утверждается.
Распределение просмотров («ступенька» между обычными роликами и хитами),
доля новых зрителей, реакция (лайки, репосты, комментарии, сохранения на
просмотр), удержание, сколько ролик прибавляет после публикации, ритм
публикаций; отдельно — чего не видно (источники трафика, первые часы,
подписчики) и что нужно, чтобы узнать. В конце — **план улучшения**: каждый
пункт ссылается на находку и говорит, какое действие в программе его
выполняет. Связи, закрытые политикой (длительность ↔ досмотры), в совет не
превращаются.

**Дашборд** (пункт 7 меню, `python -m advisor.dashboard`): один HTML-файл
в `data\runtime\dashboard.html`, открывается в браузере без интернета —
план публикаций и прогресс экспериментов, ключевые числа, просмотры по
роликам (со всеми роликами и без хитов), гипотезы, свежие несверенные
данные, эксперименты и последние идеи.

**С телефона** (Telegram, после настройки токена): `/hits` — что залетело и
почему, `/next` — последние сохранённые идеи, `/plan` — план публикаций и эксперименты. Только
чтение: идеи создаются и берутся в работу на ПК, публикации из бота нет.

## Mobile Control Layer

Телефон как пульт: Telegram показывает состояние системы и не управляет ею.
Слой **только читает** — подключение идёт под ролью `tiktok_ro`, которой
PostgreSQL не выдал ни INSERT, ни UPDATE, ни DELETE. Запрет на изменения
держится базой, а не дисциплиной обработчиков.

Внешних зависимостей нет: долгий опрос Bot API сделан на стандартной
библиотеке. Отдельного источника данных TikTok слой не добавляет.

### Setup

1. Создать бота у @BotFather и получить токен.
2. Узнать свой numeric Telegram user id (например, у @userinfobot).
3. Задать переменные окружения — в `.env` или в окружении процесса.
   В git они не попадают:

```
TELEGRAM_BOT_TOKEN=
TELEGRAM_OWNER_ID=
```

4. Проверить настройку без запуска опроса:

```
python3 -m mobile.telegram --check
```

5. Запустить:

```
python3 -m mobile.telegram
```

Нет токена или нет owner id — интеграция выключается целиком и сообщает
причину. Остальная система при этом работает как раньше.

### Безопасность

* белый список из одного владельца; любой другой пользователь получает
  `Access denied.` без внутренних подробностей;
* каждое обращение, включая отказ, пишется в append-only журнал
  `data/mobile/audit.jsonl` с `correlation_id`; журнал в git не попадает;
* токен не хранится в базе, не пишется в журнал и не печатается в логах —
  значения вычищаются редактором перед записью;
* ошибка отдаёт владельцу только `correlation_id`, подробность уходит в
  журнал и лог приложения;
* публикация остаётся выключенной: команд `/publish`, `/submit`, `/send`
  нет ни явных, ни скрытых, а бот не стартует, если
  `system_capabilities.publishing.submit` включён.
